POSMaster V3 — System Architecture

How the Electron desktop POS is built and how it connects to the data. The defining trait: the desktop app embeds its own API server in-process, so the UI never talks to the network directly — every read, write, and live update is brokered through an Electron IPC bridge to a local Express + Socket.IO server that owns the one shared MongoDB Atlas database.

The big picture

Four layers inside one desktop process, plus one shared cloud database

Everything except MongoDB and the external services runs inside a single Electron application instance (single-instance-locked). The renderer, the IPC bridge, and the online API server are three contexts of the same OS process; the server is not a separate program.

Process model

One OS process, three JavaScript contexts, one external DB

The unusual part: what looks like a client/server system is actually a single Electron app. The "server" is booted by the main process via require('./src/online-server/runtime.cjs').startOnlineServer() and runs in the same process — not spawned as a child.

Renderer context

Chromium window running the React bundle. No Node access (contextIsolation:true, nodeIntegration:false). Reaches everything through window.electronAPI.

Main process

Node.js. Owns windows, printing, auto-update, the IPC handlers, and hosts the embedded server + realtime client.

Embedded server

Express + Socket.IO on 127.0.0.1:4100, started inside main only when packaged (dev runs it as a separate online:dev process).

MongoDB Atlas

The only thing outside the process. Every till connects to the same cluster, which is how sales and stock stay consistent across terminals.

Why embed the server? It keeps one codebase and one auth/permission model for both the desktop and any future remote deployment, and it means the renderer talks to a stable local endpoint regardless of network quality. The tradeoff: each till holds its own DB connection and its own realtime hub, so cross-till propagation happens through MongoDB + each till's own event stream, not a shared broker.

Real-time sync

How a sale on one till refreshes the others in ~2 seconds

Writes emit domain events. Socket.IO carries them from the server into the main process, which pushes them into the renderer over IPC, where the reactive store invalidates the affected caches and refetches. This is the return half of the loop.

Same-till loop is guaranteed. A write and its event both pass through the one embedded server, so the terminal that made the change always refreshes.
Cross-till timing. Each till runs its own server + socket bound to the shared Atlas DB. Another terminal sees the change when its own event stream/cache cycle turns over (seconds), backed by the 2s cache TTL — not an instant shared-broker push.

Auth & sessions

JWT for identity, a server session for revocation

Login

  • bcrypt verify (cost 12); per-account lockout (5 tries / 15 min).
  • Mints a JWT: {sub, orgId, branchId, roles, sessionVersion}, expires 8h.
  • Inserts a sessions row storing only the token's SHA-256 hash, never the raw token.
  • Single active session: prior sessions for the user are deactivated.
authService.cjs:107

Every request & socket

  • HTTP: requireAuth verifies JWT + matches an active session by token hash.
  • Socket.IO: the same check runs at the io.use handshake, using handshake.auth.token.
  • When a session is replaced, the hub force-disconnects the old device's sockets.
  • Session token is pushed into the bridge before each call via syncOnlineToken().
middleware/auth.cjs · hub.cjs:17
Revocation without stateless-JWT pain: because a valid token must also match a live sessions row, logging out (or being displaced by a new login) invalidates the token immediately — server-side — even though it hasn't expired.

Receipt printing

Three paths, selected by mode

The renderer rasterizes the receipt to a canvas (html2canvas), then either builds ESC/POS bytes or a sized PDF. All three print paths live in the main process because they need Node/native access the browser can't have.

Network (thermal)

Raw net.Socket to the printer's IP on :9100, streaming an ESC/POS raster. Optional subnet auto-discovery (scans :9100, 5-min cache).

🔒 Security & Boundary Violations

Impact: The application has critical security vulnerabilities that allow unauthorized access, data leakage across organizational boundaries, and complete API compromise.

Critical Issues (Immediate Action Required)

CRITICAL CORS Wildcard Configuration
📍 config.cjs:25 | electron.cjs:487
The CORS origin defaults to '*', allowing requests from any website to the API using the user's bearer token.
Attack Scenario:
An attacker hosts a malicious website and tricks a POS operator into visiting it. JavaScript on that site makes authenticated API requests using the user's Bearer token (stored in browser memory). By bypassing same-origin policy, the attacker can create fraudulent sales transactions, escalate privileges, or exfiltrate customer data.
🚨 RISK: Complete compromise of API security. Any website can manipulate sales, inventory, and user data.
CRITICAL Organization Scope Bypass (Multi-Tenant Data Leakage)
📍 OnlineModeService.cjs:147, 221, 239, 251
Sales summary, daily sales, active sessions, and session count queries use hardcoded config.defaultOrgId instead of the authenticated user's organization, allowing cross-organization data access.
Data Leakage Scenario:
A cashier from Organization A calls electronAPI.online.getSalesSummary(). The backend queries MongoDB for sales in 'default-org' instead of Organization A. If multiple organizations share the database with 'default-org' as a fallback, the cashier sees financial data from Organization B. Complete revenue reports, customer transactions, and business metrics leak between organizations.
🚨 RISK: Complete multi-tenant isolation failure. Financial data, customer information, and competitive intelligence leak across organizational boundaries.
CRITICAL Unrestricted IPC Channel Access
📍 preload.cjs:28-29
The send() and invoke() methods are exposed without channel whitelisting, allowing the renderer to call any IPC handler by name.
Exploit Scenario:
A compromised React component (via npm supply chain attack or XSS) calls electronAPI.invoke('backend:status') or any undocumented IPC handler. The attacker can trigger internal functions not meant to be exposed through preload. This completely bypasses the documented API surface.
🚨 RISK: IPC whitelist is theater. Preload.cjs becomes documentation rather than security boundary.
CRITICAL Session Enumeration & Footprinting
📍 OnlineModeService.cjs:239
getActiveSessions() returns all active sessions across organizations using hardcoded defaultOrgId, exposing user enumeration and device tracking data.
Intelligence Gathering:
An attacker calls electronAPI.online.loginHistory.getActiveSessions(), receiving the list of all logged-in users with device names and timestamps. This data enables targeted social engineering (knowing who's online), identification of admin sessions for privilege escalation attempts, and competitive intelligence (detecting when competitors are actively using the system).
🚨 RISK: User enumeration and session fingerprinting. Enables targeted attacks on high-privilege users.

🏗️ Architecture & Topology

Impact: The dual-runtime topology, missing error propagation, and lack of instance locking create operational fragility and silent failures.

CRITICAL Silent Bundled Server Startup Failure
📍 electron.cjs:1397-1404
When the bundled online server fails to start (e.g., MongoDB unreachable), the error is caught, logged to console, then ignored. The app continues and shows generic "check connection" to the user. On Windows, console output goes nowhere.
Failure Scenario:
A till in the field tries to start. MongoDB Atlas is unreachable due to IP allowlist misconfiguration. The app starts, the server fails to connect Mongo, the error is logged to dev console (nonexistent on Windows), and the app loads with Intro.jsx polling /api/ready. User waits 45 seconds and sees "Online server unavailable. Please check the connection." with no indication of the actual problem: MongoDB unreachable, DNS failed, or network timeout. They restart the app (same failure), then call support. The real cause is buried in electron logs that don't exist on Windows.
🚨 RISK: Operational blind spot. No visibility into why tills fail. Support costs increase. MTTR (mean time to recovery) extends from minutes to hours.
CRITICAL No Single-Instance Lock
📍 electron.cjs (missing requestSingleInstanceLock)
The app has no requestSingleInstanceLock(), so two copies can run simultaneously. Both try to bind :4100; the second fails silently in a try-catch, leaving two instances with writes going through the first one's server.
Concurrency Hazard:
Operator double-clicks POSMaster. Two instances launch. Till A connects to :4100 (first instance). Till B's server fails to bind, but the app continues and connects to :4100 as well (both instances share the port). Sales entered on Till B go through Till A's server, mixing IDs and sessions. Operator doesn't realize two instances are running. Inventory desync, potential data loss.
🚨 RISK: Concurrent instance hazards, session confusion, data corruption under dual-open scenarios.
HIGH Config Fallback Chain Creates Security Blind Spot
📍 config.cjs:26 | electron.cjs:466
If MONGODB_URI is unset or empty in the packaged config, line 26 silently falls back to mongodb://127.0.0.1:27017. Empty values in JSON config are skipped (electron.cjs:466), so a till with broken config doesn't error—it tries to connect to local Mongo.
Silent Misconfiguration:
A till is built locally without proper CI secrets. The online-runtime-config.json has empty MONGODB_URI. The till starts, the online server tries to connect to localhost:27017 (doesn't exist), fails, startup is hidden from the user, and the till sits in a broken state. No error message, no indication of misconfiguration.
🚨 RISK: Misconfigurations are silent. Operational debugging becomes impossible.

💾 Data Integrity & Transactions

Impact: Event ordering gaps, incomplete synchronization, and scope issues risk data inconsistency and lost transactions.

CRITICAL Tea Coop Sync Only Fetches First 100 Members
📍 teaCoopSyncService.cjs:268-315
Members sync requests page=1&limit=100 with no pagination loop. The collection has 5,152 members; only ~2% sync per run.
Sync Failure:
First sync gets members 1-100. Second sync (next day) requests page 1 again, upserts the same 100 rows, skips members 101-5152 entirely. New members added to Tea Coop never appear in POS. Payments from members 101+ never sync. Sales can't be recorded against those members.
🚨 RISK: 98% of cooperative members never sync. Sales against them are incomplete. Revenue reporting is inaccurate.
HIGH No Outbox for Domain Events
📍 domainEvents.cjs:4-16
Events are published after transaction commits (correct ordering) but there's no outbox or retry mechanism. If the socket.io emit fails, the write is durable but the event is lost forever.
Event Loss:
A sale is committed to MongoDB. Socket.io emit fires to notify other tills of the stock decrease. Network hiccup causes emit to fail silently. The write succeeded, but other tills never hear about it and continue showing stale inventory. Customers can over-sell.
🚨 RISK: Eventual consistency violation. Distributed state can diverge permanently after failures.
HIGH Invoice Numbering Under Concurrent Load
📍 salesService.cjs | invoice_counters collection
Invoice number generation uses atomic MongoDB increment, but the implementation hasn't been stress-tested under rapid concurrent sales on a single till or multiple tills.
Concurrency Issue:
Three cashiers on Till A each ring up sales simultaneously. Two get invoice number 100, one gets 101. Accounting system tries to post invoice 100 twice. Financial reports duplicate revenue.
🚨 RISK: Duplicate invoice numbers under load. Revenue reconciliation breaks.

🛠️ Operational Readiness

Impact: Missing observability, silent failures, and manual update flows make production operation difficult.

CRITICAL No Logging, Monitoring, or Error Tracking
📍 electron.cjs, src/online-server/*.cjs
Errors are logged to console. Bundled server startup failures, Mongo connection errors, Socket.IO failures—all logged to console.error(). On Windows (the target platform), this output goes nowhere.
Operational Blindness:
100 tills deployed in the field. 10 of them have intermittent Mongo connection failures due to network timeouts. The errors are logged to Windows console (invisible). Support receives complaints ("sales won't go through some days"). No metrics, no logs, no traces. Support troubleshoots by calling operators and asking them to look at a non-existent console.
🚨 RISK: Complete operational blindness. MTTR extends from minutes to days. Support costs spike.
HIGH No Health-Check Before Server Start
📍 runtime.cjs:9-49
The bundled server immediately calls connectMongo() without pre-flight checks. If Mongo is unreachable, the entire startup fails silently.
Failure Without Diagnosis:
Till starts. Attempts Mongo connect. Timeout after 30s. Fails. No indication of DNS failure, IP allowlist rejection, or network unreachability. Just "online server unavailable."
🚨 RISK: Failures are not debuggable. Tills hang on startup.
HIGH Printer Autodiscovery Scans Entire Subnet
📍 printing.js:223-310
Thermal printer autodiscovery enumerates every IPv4 on the local subnets, TCP-probes port 9100 in batches, with 250ms timeout. On a /24 network (256 hosts), this takes ~30 seconds every 5 minutes (cached).
Network Performance:
Till starts in a busy enterprise network with a /23 subnet (512 hosts). Autodiscovery scans 512 hosts at 250ms each. Sales come to a halt for 2 minutes while discovery runs. Customers waiting in line, cashier can't ring up transactions.
🚨 RISK: UX freezes during printer discovery. Network load spike.

🧹 Code Quality & Maintainability

Impact: Dead code, silent errors, and large components increase bug risk and slow development.

HIGH Silent Wrong Answers in Legacy Shims
📍 OnlineController.cjs:161-225
Legacy compat channels like categories:search, users:search, restocks:get-by-date-range accept filter arguments, discard them, and return the full list. No error thrown.
Silent Bug:
Frontend calls electronAPI.categories.search('Tea') expecting filtered results. Backend silently discards the query and returns all 1,115 categories. UI displays everything instead of search results. Operator thinks the search is broken, doesn't realize it's the wrong data.
🚨 RISK: Silent data errors. Difficult to debug. Encourages reliance on broken shims.
HIGH Incomplete Handler Removal
📍 index.cjs:30-34
The unregisterAllHandlers() function logs but never actually calls ipcMain.removeHandler(). Handlers are not removed; they just persist.
Handler Leak:
App enables/disables features by registering/unregistering IPC handlers. unregisterAllHandlers() is called but does nothing. Handlers accumulate in memory. After many enable/disable cycles, the app has thousands of dead handlers consuming memory. Memory usage grows without bound.
🚨 RISK: Memory leak from handler accumulation.
MEDIUM Dead Code: eventBroadcaster.cjs
📍 src/backend/utils/eventBroadcaster.cjs (270 lines)
This entire file has zero requires anywhere in the codebase. Dead code that's never used.
Increases codebase surface area, distracts developers, consumes disk/memory, unclear if it's intentional.
MEDIUM Logout-on-Close Never Fires
📍 electron.cjs:1009 | createWindow() (never called on startup)
The close event handler (which calls performLogoutAndQuit) is inside createWindow(), which startup never calls. The window is built inline at line 1255 without a close handler.
Logout Skip:
Operator closes till window. performLogoutAndQuit() isn't called. Session remains active on the server. If till is recycled and used by another operator, the session may still authenticate to the new user until it expires (8 hours later).
🚨 RISK: Session doesn't end on window close. Multi-user exposure on shared hardware.

🗺️ Remediation Roadmap

Prioritized by severity and impact. Phases can overlap; aim for 90% of critical issues resolved within 2 sprints.

🚨 Phase 1: Critical Security Fixes (Sprint 1)
1
Fix CORS Configuration
Set ONLINE_API_CORS_ORIGIN to specific domain (or IP range for development). Remove wildcard defaults. Enforce in both config.cjs and electron.cjs bundled defaults. Test with `curl -H "Origin: ..." localhost:4100/api/ready`.
2
Fix Organization Scope in OnlineModeService
getSalesSummary(), getSalesDaily(), getActiveSessions(), countActiveSessions() should use the authenticated user's orgId from auth context, not hardcoded config.defaultOrgId. Implement org-scoped middleware that populates auth context. Audit all Mongo queries for org scope.
3
Remove Unrestricted IPC Channels
Delete send() and invoke() from preload.cjs. Force all IPC through documented namespace methods. If new handlers are needed, add them explicitly to preload and document them. Audit all calls to electronAPI.send/invoke in codebase and replace with documented methods.
🔧 Phase 2: Operational & Architecture Fixes (Sprint 1-2)
4
Implement Single-Instance Lock
Add app.requestSingleInstanceLock() to electron.cjs around app.whenReady(). On lock failure, exit the second instance or show "already running" dialog. Test by launching the app twice.
5
Surface Bundled Server Startup Errors
Replace silent console.error() at electron.cjs:1397-1404 with: 1) write to app.getPath('logs') file, 2) show detailed error in Intro.jsx if /api/ready is unreachable (detect DNS failure, connection refused, timeout), 3) provide actionable message to user (e.g., "MongoDB unreachable: check IP allowlist").
6
Fix Tea Coop Pagination
Implement pagination loop in teaCoopSyncService.cjs. Fetch all pages until limit is reached or empty response. Track last-synced member ID to avoid re-syncing. Add telemetry to report how many members were fetched.
7
Implement Pre-flight Health Checks
Before connecting to Mongo, check DNS resolution, network connectivity, and IP allowlist status. Provide specific error messages for each failure mode. Implement retry logic with exponential backoff.
📊 Phase 3: Observability & Logging (Sprint 2-3)
8
Implement Structured Logging
Add winston or similar logger to electron.cjs and src/online-server. Log all errors to file (app.getPath('logs')). Format: timestamp | level | component | message | context. Rotate logs daily. Include logs in app diagnostics/about dialog.
9
Add Metrics Collection
Log key metrics: Mongo connection time, API latency, sales per hour, errors per hour. Store locally, emit to cloud (optional). Build metrics into About dialog: uptime, error rate, last sync time. Enables field troubleshooting.
🧹 Phase 4: Code Quality & Maintenance (Sprint 3-4)
10
Remove Dead Code
Delete eventBroadcaster.cjs, commented-out bill.jsx, audit_events writes (it's indexed but never used). Remove legacy shims or document them as deprecated with sunset date.
11
Fix Handler Removal & Logout-on-Close
Implement unregisterAllHandlers() properly. Add close-event handler to the actual mainWindow (line 1255), not just createWindow(). Test logout flow end-to-end.
12
Refactor Large Components
Break InventoryRestock (2.6K) and SalesView (1.6K) into smaller, testable pieces. Extract state management (e.g., Zustand or Jotai). Create unit tests. Improves maintainability and reduces bug surface.
